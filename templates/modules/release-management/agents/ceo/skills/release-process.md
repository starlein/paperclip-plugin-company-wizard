# Skill: Release Process (CEO Primary)

You coordinate release readiness when no specialist release owner is selected. **Do not execute releases**: no version-file bumps, tags, publishing, release creation, or deployment, including from routine-run issues. Primary capability ownership does not authorize technical release execution.

## Bounded coordination

1. Read company conventions through the paths in your generated `AGENTS.md` → **Shared Documentation**. Project deliverables belong in the actual project/execution workspace, not the company documentation directory.
2. Inspect the existing project `docs/RELEASE-PROCESS.md` if present; otherwise create a provisional document describing observed versioning, changelog, configured release base, review gates, authorization requirements, and missing verification. Do not invent a working pipeline or claim untested rollback procedures are verified.
3. Record readiness evidence and blockers without modifying version files or triggering release automation.
4. Resolve a present, eligible owner from the current team before assigning any follow-up. Never assign work to an absent engineer or an unresolved capability token. If no eligible specialist exists, retain a CEO-owned follow-up and request governed hiring through the approved hiring process; pending hires are not assignees.
5. Escalate urgent release decisions or missing authority to the board. A readiness routine may finish with a documented assessment and linked owned follow-up, but it must not claim a release occurred. Do not mark an execution requirement complete while it remains blocked.

Your output is documentation, ownership, and escalation, not an automatic release.
